## 〇、2026-10-05 范围与顺序调整（以本节为准）

2026-10-04 至 10-05 用户重新说明了项目用途，并补充了界面、刷新和动画要求。与本文后面旧内容或 `PRODUCT_AND_IMPLEMENTATION_PLAN.zh-CN.md` 冲突时，以本节和第五节决策为准。

**项目是什么**：个人在本机使用的美股研究工具，核心是“取到数据，清楚地展示出来，辅助我自己研究”。不上线公网，但别人可以从 GitHub 下载到自己电脑上运行。没有意义的操作和功能不做。

1. **Insider 只展示，不分析**：买卖信号由用户自己判断，软件不做评分或信号逻辑。首页是 Insider 实时瀑布流，盘中能及时看到新交易；公司名和 Insider 名字可点，进入各自的交易记录；可按 ticker 或名字查询，默认最近 6 个月，可切到最近 10 笔，均可自定义；交易要显示前后 n 个交易日的涨跌。
2. **月度 / 区间分析**：看过去 n 年的价格。每只股票一次性取完整区间（另加 1 个月余量）；价格数据有效 24 小时，期间来回查看不重新下载，超过 24 小时自动删除。
3. **财报 / 事件分析**：软件提供提示词模板（由用户维护），用户去别的 AI 平台问到事件日期，把简短 JSON 贴回来，软件按日期从 Yahoo 取价再分析。不再需要 SEC 8-K 自动财报链路。
4. **展示**：用户懂统计和概率；所有分析要一看就懂：结论在前，K 线、排名、带样本数的分布统计。界面、布局和内容可以按数据重新设计，不受旧规划约束。涨跌一律蓝涨橙跌并带正负号。
5. **英文界面**：首次打开默认英文，右上角可切换中文，并记住选择。
6. **动画**：新 Insider 交易从顶部滑入（瀑布效果）；数字变化滚动并短暂闪色；首次加载用骨架占位；后台刷新、等待取数、计算都有清楚的进行中状态。遵守系统“减少动态效果”设置。
7. **首页刷新**：盘中按设定间隔自动更新；首次打开立即更新；休市时显示最近交易日的数据并写明日期（规则见 D22）。
8. **顺序**：先把现有项目做好（性能、代码结构、文档都整理清楚，避免别人看了一头雾水）→ 改为公开仓库作展示 → 再做板块研究页。

**2026-10-05 新发现（决定 S1 的内容）**：P2-A 部署后正式实例一度只要几十毫秒，但随后又变慢（首页约 2 秒、信息流约 3 秒，个别请求超时 30 秒）。原因是机械硬盘被持续占满（`/proc/pressure/io` 的 full 约 20–37%）：

- 系统状态接口每次发现“存储盘点”超过 10 分钟，就在后台遍历整个运行目录（约 130 万个文件，含备份硬链接和恢复副本），在机械硬盘上一次约 12 分钟，几乎不停地在跑。
- SEC 最新申报每次轮询都新建一条永久任务（一天约 1.5 万条），并把列表页存为永久来源文件；当天的 latest 批次不断累积任务链接（10-05 21:00 已 11,725 个），每次规划都全量加载。
- 来源文件约 32GB，其中 SEC 公司资料 JSON 约 19GB、最新申报列表页约 13GB，都可随时重新获取；真正需要永久保存的 SEC 申报原文（XML 和文本）只有约 1.3GB。
- 恢复验证会留下完整副本（原文约 31GB 加恢复库），正式 PostgreSQL 上还留有多个测试库和恢复库；`./iirp check` 的测试库也建在正式实例的 PostgreSQL 上，跑测试会和正式实例抢同一块硬盘。


## 一、出发点

### 1.1 评审确认的主要问题

| 方面 | 实测证据 | 影响 |
|---|---|---|
| 首页信息流 | `/api/v1/feed` 首屏 10–15 秒，测量中出现 503；每次打开冻结约 4.4 万个分组 ID | 规划目标 ≤1 秒，当前不可用 |
| 任务接口 | `/api/v1/jobs?limit=20` 返回 357KB、约 4 秒 | 数据与任务页、任务抽屉迟钝 |

已有检查：Ruff、TypeScript 类型检查、前端测试（52+21+5）均通过；后端完整测试最近记录为 1065 通过（GPT candidate-3），本次未重跑。

### 1.2 原则

1. **先修根因，验证与风险相称。** 停止 SHA 封存候选的流程；平时用测试和 CI，正式数据库的风险操作才备份并确认（见第四节）。不做无意义的操作。
2. **优先采用成熟开源方案**，只在本项目金融口径确实需要的地方保留自研。
3. **保留金融口径**：交易日/接受时间/发现时间分开、缺失≠零、修订按行、仅拆股调整价格，这些不改。
4. **数据范围**：SEC 申报和交易数据完整保留；价格数据按需获取、24 小时后删除（D14）。开发可用小样，但不把测试限制写成产品限制。
5. **金融计算只在后端**：前端不重复实现收益、排名、聚合公式。
6. **色弱友好**：全站上涨蓝、下跌橙，始终带正负号，不只靠颜色。
7. **正式数据库操作前先备份**：迁移或大规模删除前先 `./iirp backup`，报告预计耗时和停机时间，得到用户确认后执行；只有风险较高时才在副本上演练。

### P2 性能与存储（P2-A 已完成并部署；其余并入 S1、S2）

先写一个基准脚本 `scripts/bench_reads.py`，对恢复出来的真实数据副本测首页、信息流首屏/翻页、任务列表、公司/人员历史、交易详情的 p50/p95 和响应字节，作为前后对比依据。

**信息流**
- 用 keyset 分页加阅读水位线代替“每次打开冻结全量分组 ID 清单”：游标为 `(排序时间, id)`，会话只记 `as_of` 水位线和筛选条件；水位线之后的新内容只计数，提示“有 N 条新内容”。参考 [Use The Index, Luke: no-offset](https://use-the-index-luke.com/no-offset)。
- 维护每个分组的“当前修订”指针和排序键，列表查询不再现场计算全部修订。
- 停止写入 `feed_manifest`/大体积 `feed_session`，旧数据按宽限期清理。
- **日期异常**：交易日期晚于 SEC 接受日期的明显异常（2026-10-04 评审时有 5 行，如 Apnimed 2036 年、NightFood 2031 年，疑为申报人填错年份；按“晚于接受日”规则，10-05 恢复副本中共 14 行，另 9 行只晚 1–4 天）标为“日期异常、待核对”，不参与“最新实际交易”排序和日期范围摘要；原始值保留，并在详情中显示。

**任务接口**
- 列表只返回精简字段（不带 `checkpoint`/`result`/`target` 大 JSON），详情接口再取完整内容；分页加对应索引。

**存储瘦身**
- `sec_discover` 轮询不再每次生成一条永久任务：轮询进度记在每个来源一行的游标表；或至少对终态轮询任务保留 14 天。其他终态任务按规划 18.4 保留 90 天摘要。
- `source_observation`：同一来源地址内容哈希未变时只更新最后观察时间，不新增行。
- 交易 JSONB 去掉 `raw_xml`，改为引用 `source_object` + 原文行位置；交易详情需要原文时按引用读取。
- 清理后执行 `VACUUM (FULL)` 或 [pg_repack](https://github.com/reorg/pg_repack) 回收空间（在维护窗口内）。

**数据结构**
- `transaction_event` 增加类型化列：交易代码、买入/卖出方向（A/D）、股数、单价、直接/间接、持有后股数、证券名称；JSONB 只保留非常用字段。
- 新增 `transaction_owner(transaction_id, owner_id)` 关联表及索引，人员历史改用关联表查询。
- 主键继续用字符串 UUID（改类型代价大、收益小），不在本阶段变更。

**数据库资源**
- PostgreSQL 内存上限 768MiB → 2GiB，按 [PGTune](https://github.com/le0pard/pgtune) 设定 `shared_buffers`、`work_mem`、`effective_cache_size`，写进 `deploy/compose.yaml`。

| latest 扫描从不“完整” | 每轮受 1 页预算限制，没有上一次完整扫描就没有水位线，于是永远不完整，连续性水位线从未建立；工作时段每小时生成 1000–1900 条 `sec_discover`（job 表一天约 +1.2 万行、+80MB），SEC 请求平均约 0.5 次/秒（仍受 2 次/秒限制）。当天的 latest 批次不断累积任务链接（10-05 13:30 开盘创建，21:00 已有 11,725 个），每次规划都加载全部链接：07:30–21:00 规划语句超时 5 次、规划锁超时（55P03）149 次、任务提交锁超时 239 次，均由重试消化，没有任务因此失败 | 采集逻辑，较复杂，本次不改、不放宽超时；与 P2-B“轮询不再生成永久任务”一起处理，并确定水位线的建立规则（优先级高：交易日内会越来越慢） |
| 恢复验证副本累积 | CLI `restore-verify` 保留完整副本（全部原文约 31GB + 恢复库），9/09–9/24 的 4 份占约 56GB + 4.4GB，磁盘一度 93%；本次验证需约 53GB 空闲 | 经用户同意删除 9/23、9/24 两份；需要为验证副本定保留规则（如默认验证后丢弃，或只留最近一份） |

| 外部来源网络 | 同期 1 个 SEC 扫描 `ConnectError` 3 次失败、1 个财报候选 yfinance 超时 3 次失败 | 按现有重试规则处理，未放宽 |

### S1 减负，恢复正式实例性能

目标是让正式实例在 worker 正常运行、盘中时段依然快，不再被无谓的磁盘读写拖慢。

- **存储盘点不再遍历文件系统**：原文大小取自 `source_object` 表，备份和恢复副本的大小取自各自清单，数据库大小取自 PostgreSQL；精确核对改为数据页手动触发，后台最多每天一次。系统状态接口不再顺手启动盘点。
- **SEC 最新申报轮询**：不再每次轮询新建永久任务，轮询状态（上次看到的位置和时间）记在每个来源一行；查清并修正 latest 扫描“从不完整、水位线建立不起来、当日批次链接无限累积”的问题；新抓到的列表页、索引文件和公司资料 JSON 只短期保留（7 天），过期自动删除。SEC 限速（每秒 ≤ 2 次）不变。
- **恢复验证副本**：验证通过后删除副本原文和恢复库，只保留验证报告。正式 PostgreSQL 上遗留的恢复库和测试库（如 `iirp_v1_test_restore_*`、`iirp_v1_restore_*`、`iirp_v1_test_sec_*` 等）逐个确认不再使用后删除；9/09、9/13 两份旧恢复副本（迁移 0006）一并删除。
- **测试数据库隔离**：`./iirp check` 改为启动独立的临时 PostgreSQL 容器（数据放 tmpfs），跑完删除，不再在正式实例的数据库服务器上建测试库。
- **完成标准**：盘中 worker 正常运行时，正式实例首页和信息流首屏 p95 ≤ 500ms；`/proc/pressure/io` 的 full avg300 前后对比明显下降；新增 `sec_discover` 任务接近 0；盘中 SEC 新申报从被接受到出现在首页 ≤ 2 分钟。

### S2 数据保留简化

- **价格 24 小时缓存（D14）**：每只股票一次请求取“所需区间 + 前 1 个月余量”，存入缓存表并记下获取时间和到期时间；24 小时内的分析、图表、前后 n 日都复用；到期由维护任务删除；分析结果与缓存同生命周期。首页报价另有更短的缓存。
- **删除不再需要的永久机制**：价格版本与修订核对（`price_dataset_version`、`market_bar_revision`、`dataset_bar` 等）、长期维护集合和每日行情更新、研究结果冻结/复用/共享计算中不再需要的部分、Yahoo 返回的永久来源文件。删除前用 `git grep` 确认引用，相关测试一并删除。
- **清理历史数据**：可重新获取的 SEC 列表页（约 13GB）、公司资料 JSON（约 19GB）、Yahoo 返回及其 `source_observation` 记录；历史 `sec_discover` 任务和超过 90 天的其他终态任务；交易 JSONB 里的 `raw_xml`（原文在 SEC XML 文件里）。**永久保留 SEC 申报原文（XML 和文本，约 1.3GB）和全部交易数据。**清理后执行 `VACUUM FULL` 或 [pg_repack](https://github.com/reorg/pg_repack)。备份只保留最近 2 份，旧备份删除后硬链接占用的空间随之释放。
- **行情可靠性**：去掉 `yfinance._http` 私有引用；数据过期时在页面醒目提示（属于 S5 的展示，这里提供接口字段）。
- **正式库操作**：先备份；大删除分批进行；执行前向用户报告预计耗时和停机时间并得到确认。
- **完成标准**：数据库 ≤ 1.5GB；来源原文 ≤ 2GB；每日自动备份 ≤ 10 分钟；同一分析 24 小时内重复打开零外部请求，过期后自动重新获取。

### S3 财报与事件改为 AI-JSON

- **提示词模板**：财报、事件各一份，默认提供中英两版；在对应页面直接编辑、复制、恢复默认；作为用户数据长期保存。
- **精简 JSON**（示例）：`{"events":[{"ticker":"AAPL","date":"2025-10-30","session":"after_close","name":"FY2025 Q4 earnings","fiscal_year":2025,"fiscal_quarter":4}]}`。`session` 为 `before_open` / `during` / `after_close` / `unknown`，决定反应日是哪一天；`fiscal_year`、`fiscal_quarter` 只用于财报；可选 `note`。现有已保存的事件集迁移到新格式。
- **流程**：粘贴 → 校验（指出具体哪一条、哪个字段有问题）→ 预览 → 取价（24 小时缓存）→ 分析。用户保存的事件集长期保留，可删除。
- **删除**：SEC 8-K 自动财报链路（`earnings_data.py`、`earnings_planner.py`、`earnings_evidence` / `earnings_candidates` 任务等）和数据页“财报核对”。
- **完成标准**：从复制提示词到看到结果不超过 3 步；格式错误能定位到具体字段。

**完成标准**
- 切换视图、排序、周期、下钻不触发任何外部行情请求（以来源请求计数验证）。
- 排行接口 p95 ≤ 300ms（缓存命中）。
