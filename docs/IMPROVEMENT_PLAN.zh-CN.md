# IIRP2 改进计划

日期：2026-10-04。状态：**计划已确认（2026-10-04），尚未实施。** 进度见第七节。 依据是 2026-10-04 的全面评审（代码、运行实例、页面截图、接口实测、只读数据库统计），以及用户此前讨论确定的“美股板块研究页面”需求。本计划取代 `REFACTORING_PLAN_2026-09-26` 中尚未完成的 H 阶段做法。

## 一、出发点

### 1.1 评审确认的主要问题

| 方面 | 实测证据 | 影响 |
|---|---|---|
| 首页信息流 | `/api/v1/feed` 首屏 10–15 秒，测量中出现 503；每次打开冻结约 4.4 万个分组 ID | 规划目标 ≤1 秒，当前不可用 |
| 任务接口 | `/api/v1/jobs?limit=20` 返回 357KB、约 4 秒 | 数据与任务页、任务抽屉迟钝 |
| 存储 | 数据库 4.0GB：`job` 1.1GB（约 25 万条 `sec_discover` 轮询）、`source_observation` 0.9GB；交易事实仅约 9.3 万行 | 记账数据约为业务数据 10 倍，继续增长 |
| 重复存储 | 每条交易 JSONB 内含 base64 原始 XML（约 2.2KB），原文已另存文件 | 表膨胀、读取变慢 |
| 数据库资源 | PostgreSQL 内存 722/768MiB；宿主有 30GB 内存 | 资源上限过紧，造成超时和长尾 |
| 数据结构 | 交易核心字段在 JSONB；申报人是 JSON 数组，无关联表/GIN 索引；分析结果三种存储形态并存 | 查询慢、难维护 |
| 行情 | yfinance 连续失败 8 次，首页报价停在 9/24 仍标“休市报价”；引用 `yfinance._http` 私有模块 | 数据陈旧却不提示；升级易断 |
| 界面 | 说明文字过多、工程用语外露、加载与“已到末尾”同时显示、“需要处理 10238”、57 处原生折叠三角、月度页 6000px 高 | 难读、难找重点 |
| 交易表 | 同一申报 6 行看起来完全一样，实际是买入/卖出 × 直接/间接，表格缺这两列 | 误读交易行为 |
| 配色 | 涨绿跌红 | 用户红绿色弱，需改为蓝涨橙跌 |
| 前端代码 | 装了 Tailwind 但 491 处 className 仅 4 处使用，另有 2164 行手写 CSS；主要读接口返回 `dict[str, Any]`，前端为 `any` | 样式难统一，类型约束失效 |
| 后端代码 | 60 个模块平铺，`lifecycle.py` 2189 行；`Events.tsx` 2536 行 | 修改风险高 |
| 发布 | 无 LICENSE；`work/` 4.6GB 未被 `.gitignore` 排除；`refs/codex/*` 引用 1.3 万个 `work/` 对象（.git 599MB）；约 30 个文档含本机路径；`frontend/design` 29MB 被跟踪；每个 PR 跑 180 分钟验证 | 不能直接上传 |

已有检查：Ruff、TypeScript 类型检查、前端测试（52+21+5）均通过；后端完整测试最近记录为 1065 通过（GPT candidate-3），本次未重跑。

### 1.2 原则

1. **先修根因，再做验证。** H 续验中的压测失败（WorkerOwnershipLost、长尾）主要源于上表的性能和存储问题。停止 SHA 封存候选的流程，改为“改动 → 针对性测试 → `./iirp check` → 基准对比”。
2. **优先采用成熟开源方案**，只在本项目金融口径确实需要的地方保留自研。
3. **保留金融口径**：交易日/接受时间/发现时间分开、缺失≠零、修订按行、仅拆股调整价格，这些不改。
4. **完整产品目标不缩水**：开发可用小样，正常使用仍保留完整采集和回补范围（见 `config/collection-defaults.toml`）。
5. **金融计算只在后端**：前端不重复实现收益、排名、聚合公式。
6. **色弱友好**：全站上涨蓝、下跌橙，始终带正负号，不只靠颜色。
7. **改动前先备份**：涉及现有 4GB 数据库的迁移，先 `./iirp backup`，在恢复出的 `iirp_v1_test_*` 副本上演练，再应用到正式库。

## 三、各阶段内容

### P0 收口保全

- 把当前约 300 项修改/未跟踪源码在 `codex/data-lifecycle` 分支本地提交为检查点（不推送）。
- `work/`（4.6GB 过程证据）移到仓库外，例如仓库同级的 `IIRP2-archive/work-2026-10-04`。同一文件系统内 `mv` 不占额外磁盘（当前磁盘已用 88%）。

**完成标准**：`git status` 干净；`./iirp check` 结果与归档前一致；归档目录可读。

- 提交身份改为 GitHub noreply 邮箱，不再使用本机主机名。
- 补 `LICENSE`（所有者选定），保留并核对 `THIRD_PARTY_NOTICES.md`。

**内容清理**
- 文档精简为：README、产品规划、决策、架构（新增 `docs/ARCHITECTURE.zh-CN.md`）、运行手册、部署说明、API 约定、本改进计划。约 25 个带日期的过程报告、验收报告、`frontend/design`（29MB）、`docs/reports` 日志移到仓库外归档。
- 删除根目录重复的 96KB 规划副本。
- 清除文档和配置中的本机路径（用户主目录路径）。`AGENTS.md` 改为通用说明。

**CI 与安全**
- 快速 CI（目标约 10–15 分钟）：Ruff、pytest（GitHub Actions 的 PostgreSQL service 容器）、OpenAPI 生成物一致性、TypeScript 类型检查、前端测试、构建。

- [gitleaks](https://github.com/gitleaks/gitleaks) 秘密扫描（本地一次 + CI）、Dependabot（pip/npm/Actions）、保留 actionlint。可选 [pre-commit](https://github.com/pre-commit/pre-commit) 统一本地钩子。

**完成标准**：全新目录 `git clone` → 按 README 用 Compose 安装启动成功；CI 绿；gitleaks 无发现；仓库体积 < 20MB。

### P2 性能与存储

先写一个基准脚本 `scripts/bench_reads.py`，对恢复出来的真实数据副本测首页、信息流首屏/翻页、任务列表、公司/人员历史、交易详情的 p50/p95 和响应字节，作为前后对比依据。

**信息流**
- 用 keyset 分页加阅读水位线代替“每次打开冻结全量分组 ID 清单”：游标为 `(排序时间, id)`，会话只记 `as_of` 水位线和筛选条件；水位线之后的新内容只计数，提示“有 N 条新内容”。参考 [Use The Index, Luke: no-offset](https://use-the-index-luke.com/no-offset)。
- 维护每个分组的“当前修订”指针和排序键，列表查询不再现场计算全部修订。
- 停止写入 `feed_manifest`/大体积 `feed_session`，旧数据按宽限期清理。
- **日期异常**：交易日期晚于 SEC 接受日期的明显异常（2026-10-04 评审时有 5 行，如 Apnimed 2036 年、NightFood 2031 年，疑为申报人填错年份；按“晚于接受日”规则，10-05 恢复副本中共 14 行，另 9 行只晚 1–4 天）标为“日期异常、待核对”，不参与“最新实际交易”排序和日期范围摘要；原始值保留，并在详情中显示。

**任务接口**
- 列表只返回精简字段（不带 `checkpoint`/`result`/`target` 大 JSON），详情接口再取完整内容；分页加对应索引。

**存储瘦身**
- `sec_discover` 轮询不再每次生成一条永久任务：轮询进度记在每个来源一行的游标表；或至少对终态轮询任务保留 14 天。其他终态任务按规划 18.4 保留 90 天摘要。
- `source_observation`：同一来源地址内容哈希未变时只更新最后观察时间，不新增行。
- 交易 JSONB 去掉 `raw_xml`，改为引用 `source_object` + 原文行位置；交易详情需要原文时按引用读取。
- 清理后执行 `VACUUM (FULL)` 或 [pg_repack](https://github.com/reorg/pg_repack) 回收空间（在维护窗口内）。

**数据结构**
- `transaction_event` 增加类型化列：交易代码、买入/卖出方向（A/D）、股数、单价、直接/间接、持有后股数、证券名称；JSONB 只保留非常用字段。
- 新增 `transaction_owner(transaction_id, owner_id)` 关联表及索引，人员历史改用关联表查询。
- 主键继续用字符串 UUID（改类型代价大、收益小），不在本阶段变更。

**数据库资源**
- PostgreSQL 内存上限 768MiB → 2GiB，按 [PGTune](https://github.com/le0pard/pgtune) 设定 `shared_buffers`、`work_mem`、`effective_cache_size`，写进 `deploy/compose.yaml`。

**待修稳定性问题**（2026-10-04 本机 `./iirp check` 观察，GitHub CI 上均未复现；修复时不得放宽租约、锁或超时预算。2026-10-05 在 2GiB 演练 PG 上的两次完整检查：第一次除本次改动引起、已修复的用例外仅保留期测试失败，第二次 1081 通过、0 失败）

| 测试 | 现象 | 判断 |
|---|---|---|
| `test_event_compute_capacity::test_accepted_notes_survive_real_pool_frozen_reads_and_exports[ascii_17mib]` | 本机两次都返回 503 `database_timeout` | 与 PG 768MiB 上限有关；2026-10-05 在 2GiB（D13）的演练 PG 上两次完整检查均通过，正式实例待部署后复测 |
| `test_maintenance_lifecycle::test_real_long_backup_control_and_group_reaping[renew/pause/cancel/expired/token/parent_stop/child_sigkill]`、`test_sigkill_parent_is_detected_by_child_during_blocking_dump` | 首轮在高负载下 8 秒有界等待超时；单独重跑 7/8 通过，`[renew]` 另在线程未退出处失败 | 偶发，对机器负载敏感；考虑让等待按进程状态而不是固定 8 秒 |
| `test_event_overlap_reads::test_frozen_interval_endpoint_and_missing_window_pages` | 夹具 `TRUNCATE` 锁超时（setup 阶段） | 偶发，疑为上一个用例的连接尚未释放；重跑通过（10-05 两次完整检查均通过） |
| `test_maintenance_lifecycle::test_retention_daily_weekly_pin_and_corruption` | 10-05 UTC 01:00 左右运行失败，01:20 后通过 | 测试按“当前时间 − 1 小时”造备份、再减 20 分钟造“同一天”的重复备份，恰在午夜后 1 小时内运行时两者跨日；应把时间锚定到当天中午，与产品逻辑无关 |

**完成标准**（在当前真实数据量上）

| 指标 | 现在 | 目标 |
|---|---|---|
| 信息流首屏 p95 | 10–15 秒 | ≤ 500ms |
| 信息流翻页 p95 | — | ≤ 300ms |
| 任务列表（20 条） | 357KB / ~4 秒 | ≤ 30KB / ≤ 200ms |
| 公司/人员历史 p95 | 未测 | ≤ 500ms |
| 数据库体积 | 4.0GB | ≤ 1.5GB（同等业务数据） |

迁移在备份恢复副本上演练并记录耗时；`./iirp check` 全部通过；页面实际可用。

### P3 行情与界面基础

**行情可靠性**
- 去掉 `yfinance._http` 私有引用，改用公开接口创建会话。
- 首页和各页面显示数据日期与“已过期 N 个交易日”的醒目提示；连续失败时说明原因和下次重试时间，不再把陈旧报价标成“休市报价”。
- 每日收盘后更新时重拉最近 10 个交易日覆盖供应商更正；发现拆股/分红/复权因子变化时，重新核验受影响历史（规划 14.4 已有约定，核对实现）。
- 行情适配器保持可替换。备用源暂不接入，只在适配器层预留；若 yfinance 持续不可用再评估（如 Stooq、Tiingo 免费档），换源前先列出缺口和费用。

**设计基础**
- 配色令牌：上涨蓝、下跌橙（色弱友好，带正负号），选中/主操作改用不与涨跌冲突的颜色（如深靛蓝或中性深色），先实测对比度。替换全站涨跌颜色，包括分析热力表与信息流标签。
- 逐步采用 [shadcn/ui](https://github.com/shadcn-ui/ui)（项目已有 Radix 与 Tailwind）：Tabs、Select、Table、Collapsible、Tooltip、Badge、Sheet、Dialog。新组件用 Tailwind，旧 CSS 随页面改造逐步删除。
- 数据表格用 [TanStack Table](https://github.com/TanStack/table)，长列表用 [TanStack Virtual](https://github.com/TanStack/virtual)。
- 前端请求改用 [openapi-fetch](https://github.com/openapi-ts/openapi-typescript/tree/main/packages/openapi-fetch)，路径和参数有类型。

**接口类型**
- 为信息流、公司/人员历史、交易详情、系统状态定义明确的 Pydantic 响应模型，替换 `GenericOutput`，重新生成前端类型。

**界面问题修复**
- 交易表增加“买入/卖出”和“直接/间接”列，相同行为合并显示时注明条数。
- 加载中与“已到末尾”不再同时出现；空列表说明原因并提示其他筛选里有数据。
- “需要处理 10238”改为按原因分组计数（来源被拒、解析失败、待核对…），每组给一个处理入口。
- 顶部任务入口统一命名。
- 文案精简：每个区块只留一行状态；来源、版本、核验细节收进提示框或“详情”。去掉“通道”“本次阅读”“跟随最新/固定快照”等内部用语，内部标识（如 `monthly`）不出现在界面。
- 月度分析页分成“概览 / 分布 / 逐年明细 / 方法”几个页签或分段，首屏只放结论。
- 原生 `<details>` 换成统一的 Collapsible 样式。
- 拆分超大页面：`Events.tsx`、`Analysis.tsx`、`Data.tsx`、`Details.tsx` 按区块拆组件。

**信息呈现：结论先行**

现状是数据和口径基本正确，但页面先讲“数据怎么来的、是否可靠”，再给结论，而且结论通常要用户自己从表里拼出来。改为每页首屏用一句事实性结论回答该页的问题，口径和来源放进提示框或“方法”区。只陈述可核对的事实，不做评分或推荐（规划 0.2）。

- 行情卡：只留“名称 / 数值 / 带符号涨跌 / 一行数据日期”；陈旧时这一行变成醒目的“已 N 个交易日未更新”。
- Insider 信息流的“重点”：现在等于“全部衍生品行 + P + S”，衍生品行多为授予和行权，噪音大。改为突出数据里已有但界面未用的客观事实：公开市场买入（代码 P）、持股变化比例（由 `shares_after` 计算）、是否 10b5-1 计划交易（`raw_10b5_1_flag`）、申报时职务（CEO/CFO/董事/10% 股东）、多人同期买入（同公司多名内部人数日内买入）。
- 每张信息流卡片一句话：“CEO 某某 公开市场买入 $1.2M（持股 +15%），9/30 交易、10/2 披露”。
- 交易详情首行用白话解释交易代码，例如 J 配对的 A/D 加直接/间接：“直接持股转入间接持股，持股总量不变，非买卖”。证券身份未核对时，用申报中的 ticker 给出带“待核对”标记的价格窗口，而不是整块不显示。
- 月度/区间分析首屏是一张结论卡：“9 月：AAPL 8 年中 3 年上涨，中位 −3.8%；跑赢标普 x/8 年，中位落后 1.7 个百分点；样本仅 8 个，与随机涨跌无法区分。”下方紧跟逐年散点图和“年份×月份”热力表（规划要求在上方，现在在页面最底部）。
- 1—12 月表从每月 4 行（其中“股票”与“股票（共同样本）”两行数值相同）共 48 行，改为每月 1 行：中位、上涨 x/N、跑赢基准 x/N、中位超额，可排序；箱线和分位数放进展开项。
- 普通研究界面不显示内部 ID（目前热力表上方显示数据哈希和结果 UUID，违反规划 4.4）。
- 数据与任务页首屏回答“系统是否正常”：正常就一行“正常”；有问题按原因列出（如“yfinance 连续失败 8 次，下次重试 …”），不显示“需要处理 10238”这类总数。

**完成标准**：1366×768 和 1440×900 截图逐页检查；每个页面首屏第一句话能回答该页的问题；行情过期能在首页一眼看出；前端类型中不再有 `any` 的主要读接口；色弱模拟（如 Chrome DevTools 的 deuteranopia 模拟）下涨跌可分辨。

### P4 板块研究

需求来自用户此前讨论（11 个大板块、25 个行业组）。按以下方式接入本项目：

**数据（复用现有行情管线，不另建 SQLite）**

**计算（全部在后端）**

**开发顺序**（沿用讨论结论）
1. 11 大板块数字排行、统一口径、长期维护与缓存。
2. 行业组映射、下钻、勾选比较。
3. 热力图与纵向 K 线。
4. 接入近 8 年月度与区间分析；先按 D6 把现有月度/区间引擎切换为“开盘 → 收盘”口径（旧结果保留原口径并标注），再让板块页复用。

**完成标准**
- 切换视图、排序、周期、下钻不触发任何外部行情请求（以来源请求计数验证）。
- 排行接口 p95 ≤ 300ms（缓存命中）。
- 手算样例：至少 2 只 ETF 的 1 个月与某年 10 月收益，与本地日线手算一致；XLC 的 2018 年样本按实际上市日期处理。
- 下钻后返回，周期、排序和勾选保持不变。

### P5 SEC 历史回补改造

- 历史回补改用 SEC 官方 [Insider Transactions Data Sets](https://www.sec.gov/data-research/sec-markets-data/insider-transactions-data-sets)（Form 3/4/5 结构化季度数据）：每季度一个文件，替代数十万次逐份请求。
- 实时部分保持现有链路：Atom 最新申报 + 日索引 + 逐份 XML 原文。
- 两条链路写入同一规范化交易表；用数据集与逐份解析结果交叉核对，差异进入待核对，不静默覆盖。
- 可用 [edgartools](https://github.com/dgunning/edgartools) 作为解析结果的独立比对（只用于测试，不必成为运行依赖）。

**完成标准**：8 年回补总请求数从“每份申报一次”降到“每季度一次”量级；交叉核对差异率有报告；实时链路不受影响。
